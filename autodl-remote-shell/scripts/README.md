# scripts 说明

## 首要认知：这些脚本不在本机执行

本目录下的 `.sh` 是**给远端 AutoDL 实例跑的诊断脚本**。在本机双击/直接执行它们**没有意义**——
它们探测的是容器内的磁盘、cgroup 配额、GPU 与端口，本机上要么命令不存在，要么得到的不是目标机器的信息。

之所以**做成 shell 而不是纯说明文档**，是因为这些组合命令（尤其是"读 cgroup 而不是 free"、"codeload 而非 git clone"）
每次现场重拼必然会退化。固化为脚本 = 命令正文只有一处真身，可复用、可校验。

**详细原理与踩坑根因不写在这里**，见上层 `references/`（脚本负责"执行什么"，references 负责"为什么"）。

## 执行范式

### 范式 A：短命令 —— 把脚本正文直接作为 command 发送

本目录下两个脚本都是**秒级只读**命令，因此最干净的做法是：
读取脚本文件内容，把**正文整段**作为 `execute_command` 的 `command` 参数发过去，连同实例连接信息一起：

```json
{
  "command": "<此处粘贴脚本正文>",
  "host": "<实例SSH主机>",
  "port": <实例SSH端口，整数>,
  "username": "root",
  "password": "<实例密码>"
}
```

优点：一次调用完成全部检查；**远端不残留任何脚本文件**。

> 正文中若有分层 heredoc/`echo`，注意保持原样换行即可，远端 bash 会正常解析。

### 范式 B：长任务 —— 不建议直接用本目录脚本

本目录脚本均为只读诊断，属短命令，走范式 A 即可。

若是**下载/编译/安装**这类分钟到小时级的任务，不要用"正文直发"（超过工具响应窗口会返回**空输出**，
看起来像失败实则仍在跑）。应改为：先在远端写脚本文件 → `setsid` 后台 → 轮询日志。
详见 `references/shell-mcp-usage.md`。

## 脚本清单

### `autodl-instance-probe.sh`

**用途**：新拿到一台实例时一次性摸清家底。

检查项：

- 系统盘 `/` 与数据盘 `/root/autodl-tmp` 的剩余空间（决定模型放哪、能放多大）
- **容器真实配额**：读 `/sys/fs/cgroup/memory.max`、`cpu.max`（纠 `free`/`nproc`/`lscpu` 的宿主机虚值）
- GPU 显存与驱动
- Python 是否在 PATH、`venv+ensurepip` 是否可用
- `/etc/network_turbo` 是否存在及其代理地址
- ModelScope 直连、GitHub codeload 走 turbo 的实测速率

**预期输出**：分段标题 + 结尾一段"体检结论要点"清单。

**注意**：脚本会 source 一次 turbo 并拉取约 2MB 的采样数据用于测速；全程只读，约 10–30 秒完成。

---

### `autodl-port-check.sh`

**用途**：排查"实例内服务为什么外网访问不到"。

检查项：

- 列出全部监听端口
- 逐个确认 **6006 / 6008** 是否在监听，并做本机 `curl` 自检（根路径 + `/health`）
- **预警**：是否有服务正跑在不会被映射的端口上（8080 / 7860 / 8000 / 11434 / 8888 / 5000 / 3000 / 8501）

**预期输出**：端口明细 + 结尾"结论与动作建议"（含各服务改端口的具体参数）。

**注意**：只做观测，不启动也不停止任何服务。

## 修改脚本时的两条硬约束

1. **保持只读**：正文不要出现删除类命令（尤其带前置 `;` 的 `rm -rf`）、`pkill` 等。
   一旦命中 shell MCP 的安全过滤，**整条命令一行都不会执行**，
   且会返回「命令被拒绝执行」——排查时极易误判为"没跑起来"。
2. **保持自包含**：不依赖在远端先落盘、不 `source` 外部文件、用绝对路径。
   因为范式 A 是"正文直发"，远端上并不存在这个脚本文件本身。
