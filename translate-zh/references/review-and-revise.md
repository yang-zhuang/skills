# 独立评估与修订（单轮终审）

> 本文管「译文交付前的质量关卡怎么运转」。翻译执行规则见 execution-rules.md。
> 评估→修订是**有界循环**：评、修、按幅度复核，封顶 2 轮评估（见 §1.3）。
> 无条件全文多轮循环已于设计期否决（理由见 design-principles.md §7）——
> 否决的是"无界"，不是"循环"。

## 1. 评估 agent：全新、只面对两份文本

评估 agent 由**全新调用**担任（与翻译执行者无关的新会话 / 新 sub-agent），
**不知道翻译过程**（分了几块、执行者报过什么、主 agent 改过哪里）。派工时只
给定这 4 个文件（文件清单式派工，评估不分块、无隔离问题，无需 bundle）：

1. 源文（分块 run 给剔除后的 clean 版）
2. 译文（final.zh.md）
3. `data/glossary.yaml`
4. 本文

新鲜眼睛是评估的全部价值：过程知识造成确认偏误（"我知道这里为什么这么翻"，
于是放过本该报的问题）。除清单外禁止读项目其它文件。

### 1.1 只查硬错误，风格一律不评

| 查（硬错误） | 不查（风格偏好） |
|---|---|
| 漏译、多译 | 句式是否流畅 |
| 事实 / 数字错误、单位被换算（7B→70 亿） | 连接词取舍 |
| 术语违表（对照 glossary.yaml） | 语气强弱 |
| 链接 / 图片丢失或失效 | 段落长短 |
| 代码块 / 命令 / 路径被改动 | 同义润色 |
| markdown 结构破损、公式被改动 | — |

风格判断交给人 —— 人看一眼比模型判三轮准。评估 agent 对风格有意见，写在报告
最末「风格备忘」一节，仅供参考，不算问题、不触发修订。

**「翻译说明」附录的地位（2026-10-07 明文化）**：它是译者写给主 agent/用户的
元信息区，**豁免「多译」检查**（其内容源文本无对应），但其声明的事实仍需抽查 ——
如"按 pending fallback 处理"这类援引，核对 glossary 后不实即报规则缺口。

### 1.2 建议格式（七字段，缺一不可，必须自包含）

```markdown
### S-007
- 位置：第 2 节「方法」第 3 段，锚点 "We scale the model to 7B..."
- 类型：单位误译
- 现状：把 7B 译成了「70 亿参数」
- 建议：改为「7B 参数」
- 理由：参数量按术语表保留符号，不做数量级换算
- 判定：立即修改 / 存疑（写明不确定的原因）
```

自包含的检验标准：把这条建议单独发给一个没看过原文和文档的人，他必须能看懂
「哪里、现在是什么、改成什么、为什么」。写得不清楚的建议 = 无效建议。

### 1.3 循环：评估 → 修订 → 验收（封顶 2 轮评估）

评估报告两种结局：**无硬错误** → 通过交付（「风格备忘」随附）；**有建议** →
进修订（§2）。修订不是终点 —— 判断性修订本质是重新翻译，修订者可能引入
新错误，所以验收分两层：

1. **确定性验收（每轮必跑，全文，零 token）**：术语 grep + 守恒计数 + 结构对比。
   确定性修（术语/链接）由这一层兜底即可，不需再评。
2. **判断性修订的复核（按幅度分流）**：
   - **≤ 3 处句子级** → 主 agent 逐条对照源文裁定（这是验收判断，不是翻译）
   - **> 3 处或整段重写** → 被改块重新外派评估 agent（只评该块 vs 该块源文，
     文件清单式派工，~6k/块）。**整翻 run 没有块结构，全文视为单块**：
     被改即全文重新评估（~源×2.2+7.5k），同样受 2 轮封顶约束
3. **封顶 2 轮评估**：第二轮仍报硬错误 → 再修一次 → 停。仍有遗留就在交付时
   列明「遗留项」交用户 —— 不无限循环，也不静默烂尾。
4. **停滞检测**：同一 S-id 连续两轮被报 → 标「争议」，不再自动修改，交用户裁决。

为什么封顶在 2 而不是 3 或无界：全文评估 12k/轮、块级复核 6k/块，预算是真实
约束；模型评模型的风格噪音随轮数放大；且本项目**一次评估都还没跑过**，2 轮
够不够要等首次真实数据说话 —— 现在拍更细的轮数纯属编规则。

## 2. 修订：先分确定性 / 判断性，再决定谁动手

| 建议类型 | 谁修 | 怎么修 |
|---|---|---|
| 术语统一、链接 / 图片恢复、格式修复 | 主 agent | 直接改**块文件**（不是成品！见 chunking-and-cost.md §7）→ 重新 join |
| 句子重译、漏译补译 | **全新修订 agent** | 按块组修订包外派（见下） |

**修订包 = bundle + 建议清单**：`chunk.py bundle <dir> --index N` 重新生成该块
自包含任务包，主 agent 在其后追加「本块修订建议」一节（只含定位到该块的建议）。
修订 agent 产出**整块新译文**覆盖 `NNN.zh.md`，然后重新 join。
（此组装当前由主 agent 手工追加；首次真实评估产生建议清单后即固化为 chunk.py
子命令 —— 重复手工动作必须固化，见 design-principles.md §1 工具匠职责。）
（不输出 diff —— 全量可解析、可校验；块级体量下代价可接受。）

修订 agent 同样受 execution-rules.md 硬边界约束 —— 规则本来就在包里。
若评估通过但全文无分块（整翻 run），判断性修由主 agent 按建议单点重译，
不外派（几句话的活，不值得一次 5500 的固定开销）。

## 3. 评估成本（计入成本闸门）

评估 ≈ **源 × 2.2 + ~7.5k 固定**（读源文 + 读译文 + 规则 + 术语表）。
4–5k token 的文章约 17–19k；修订 agent 派工另计（同块翻译的固定开销
~5.4k + 输出）。

**闸门口径（与 chunking-and-cost.md §2 一致）**：开翻前 `chunk.py cost`
展示给用户并对照 30000 的总账 = 翻译 + 首轮全文评估 + 首轮复核。触发第 2 轮
全文评估属计划外追加派工，执行前单独向用户补一次确认 —— 2 轮封顶意味着
追加最多发生一次，账可预期。例：2.7k 文章首轮口径 ≈ 11.5k（翻）+ 13.5k
（评）≈ 25k，可自主执行；4–5k 文章首轮口径 ≈ 33–35k，已超线，
开翻前就必须拿确认。

## 4. 修订回执

修订 agent 除整块新译文外，逐条报告：`S-007 采纳` / `S-008 驳回：理由`。
**驳回必须写理由** —— 这是防止全盘驳回偷懒的唯一机制。驳回的建议由
主 agent 裁定，用户否决制。

回执末尾**必含「规则缺口」一节**：执行中发现的规则问题 —— 文档没覆盖的
情况、互相矛盾的规则、照着做必然产出坏译文的标准。只报告，不修改：
修订 agent 是只见局部的临时角色，没有改规则的授权，也没有判断"这是第几次
出现"所需的全局视野；且 run 中途改规则会让后续块的 bundle 变样，流程不幂等
（权限表见 design-principles.md §5）。

## 5. 规则缺口闭环：报告 → 甄别 → 落盘

评估报告和修订回执里的规则缺口，由主 agent 统一甄别：

| 缺口出现频次 | 动作 |
|---|---|
| 单次个例 | 不动文档，记录在回执存档（防将来误判为首次） |
| **同一缺口 ≥ 2 篇** | 修对应 reference / glossary（先行落盘，用户否决制） |
| 导致本篇产出硬错误的规则 | 修规则 + 回填本篇译文（修文档和修译文是两个动作，都要做） |

这是 design-principles.md §1「第二遍即固化」原则在文档上的应用：脚本化的是
主 agent 的重复手工动作，文档化的是**跨 run 重复暴露的规则缺口**。没有这条
闭环，文档缺陷会逐篇复现 —— 每篇新文章都踩同一个坑，坑却永远没人填。
