# 提示词设计：怎么让大模型按预设标题选对应用

## 一、输入给模型的是什么

`select_apps.py` 把每个应用压成紧凑摘要（`prompt.py` 的 `build_app_summary()`）：

| 字段 | 来源 | 为什么要给 |
|---|---|---|
| `application_id` / `name` / `author` | 详情接口 | 结果要能回指到真实应用，作者辅助判断可靠性 |
| `describe` / `author_note` | 详情接口 | 作者自己写的说明常比简介更准，比如“建议 32GB 显存” |
| `tags` | `tag_list` | 平台分类，辅助主题匹配 |
| `badge`（精/热/无） | `popular_type`；前端把 `excellent` 显示成「精」、`hot` 显示成「热」 | 平台精选标记，同档位时优先 |
| `updated_at` / `update_age_days` | 应用级更新时间（列表无此字段时从版本时间推算，统一放进 `updated_at`） | 维护活跃度；超 180 天由代码先剔除 |
| `latest_version` / `latest_version_updated_at` | 详情接口 | 版本号参考；**不用作更新时间判断**，见第三节 |
| `star_num` / `download_num` / `use_num` / `runtime` | 详情接口 | 真实热度，只作同档位排序证据，不允许压倒主题匹配 |
| `versions`（前 3 个） | `version_list` | 框架、CUDA、开机命令、镜像大小，判断是否开箱即用 |
| `readme_excerpt`（1200 字） | `readme` 全文截断 | README 才写得出“有没有真正的视频工作流”这类硬证据 |

README 截断到 1200 字是为了控制提示词长度；完整原文仍在 `outputs/app_details.json`，需要人工核对时可查。
候选默认 30 个，提示词约十几万字，`agnes-3.0-flash` 实测可用。

**详情覆盖率**：`fetch_details.py` 默认只抓前 30 个。没抓详情的应用仍会进入候选，但 `readme_excerpt` 为空，
只能靠名称、简介和版本字段判断。`select_apps.py` 会在运行时打印覆盖率提醒；要严格评估全部 243 个，
先跑 `fetch_details.py 0`。

## 二、system prompt 的六条评判标准

写在 `scripts/prompts/select_system.md`（Markdown，自包含：硬边界/输入字段表/输出格式/排序标准/正反例/自检清单），按优先级：

1. **主题匹配**：标题“视频生成”时，必须是文生视频/图生视频工作流；图片生成、训练、纯聊天即使热度高也要扣分；名字带关键词但 README 没有对应工作流的同样扣分。
2. **开箱程度**：工作流、预装模型、开机命令是否写清楚；要不要额外上传权重或配复杂依赖。
3. **平台标记**：「精」优先于「热」优先于「无」，但只在主题匹配和开箱程度接近时起决定作用。
4. **更新时间**：以应用级 `updated_at` 为准；>180 天的已被代码剔除，90~180 天要在理由里提示维护偏旧。
5. **真实热度**：收藏 / 下载 / 运行时间是同档位的排序证据，不能压过主题不匹配或 README 无证据。
6. **硬件可行性**：默认系统盘能否装下、显存要求是否常见；超大镜像或超大显存要在理由里点出来。

硬性要求还包括：只能用给定资料、不编造；理由里要写清「精/热/无」「更新多久」「下载量」中至少两项；
严格输出 JSON；只排序不替用户决定。

## 三、精 / 更新时间 / 下载量：从证据到硬规则

### 「精」不是感觉，是一个字段

前端 `assets/app-item.js` 的逻辑是 `popular_type === "excellent" ? "精" : "热"`，
也就是说卡片角标「精」= `popular_type == "excellent"`，「热」= `hot`，其余不显示角标。
2026-11-24 实测 243 个应用：**9 精、4 热、230 无**。所以「精」是稀缺信号，值得作为同档位加分项，
但不应该让一个主题不匹配的应用靠角标翻盘。

### 更新时间别用错字段（重要）

你截图里看到的「更新时间 2026-11-23 11:57:01」来自**应用级 `updated_at`**
（前端 `app-details.js` 用的是 `a.value.updated_at`），不是 `latest_version_updated_at`。

| 应用 | 应用级 `updated_at`（UI 显示） | `latest_version_updated_at` |
|---|---|---|
| id=273 ComfyUI中文整合版 | 2026-11-23 11:57:01 | 2026-11-23 11:57:00 |
| id=112 西瓜AI | 2026-01-28 15:17:54 | 2026-01-24 23:41:44 |

对 id=112 两者只差几天，但对列表里只有版本时间的应用差异可能更大。脚本统一：
详情用 `updated_at`；列表无此字段时用 `version_list` 里最大的 `updated_at` 推算，统一放进
`updated_at` 字段。来源标注只在代码日志里体现，不发给模型。

### 陈旧闸门是代码做的，不交给模型

`config.STALE_DAYS` 默认 180（可用环境变量 `AUTODL_ART_STALE_DAYS` 改）。`select_apps.py` 在调用大模型
**之前**把超期应用剔除并打印名单，名单写进 `selection_<标题>.json` 的 `excluded_stale`，不会静默消失。
理由：模型对“算不算旧”不稳定，确定性规则必须放在代码里。`AGING_DAYS`（默认 90）只用于提示模型在理由里提醒。

实测 30 个详情里只有 id=112「西瓜AI」超过 180 天（299 天），被闸门剔除；id=5「llama-factory一键使用」
140 天，属于「维护偏旧」但未剔除。

### 下载量怎么用

`download_num` / `star_num` / `runtime` / `use_num` 已经全部进摘要。规则是：
主题匹配、开箱程度同档时，下载量和收藏数高的优先；但热度不能覆盖 README 无证据、镜像过大或更新陈旧。
理由里必须出现具体数值或判断，不能只写“人气高”。

## 四、输出协议（必须严格遵守）

```json
{
  "selected": [
    {
      "application_id": 273,
      "name": "ComfyUI中文整合版",
      "score": 8.5,
      "reason": "精标、内置视频工作流，更新仅 1 天；短板是镜像接近 20GB"
    }
  ],
  "summary": "一句话整体说明"
}
```

`score` 是 0~10 的数字，`reason` 中文不超过 60 字，`selected` 数量必须等于用户要的 TopN。
脚本会校验 id 是否真的在候选里、去重、不够数时按收藏数兜底并标记 `fallback: true`。
原文永远单独保存到 `outputs/llm_raw_<标题>.txt`，解析失败时直接看它，不猜。

## 五、正反例（为什么这样写）

**反例：只看名字和收藏数。**
> “MINIMAX-H3提速500高画质”收藏 2838，排第一。

问题：收藏高不等于标题匹配；README 里写的是视频生成工作流才算数。所以 prompt 明确要求
“名字带关键词但 README 没有对应工作流要扣分”，并把 README 摘要放进输入。

**反例：只看「精」角标。**
> “id=5 llama-factory 是精标，所以排第一。”

问题：它是 2026-07 更新的（140 天，维护偏旧），而且主题是训练框架不是视频生成。角标只是同档位加分项。

**正例：证据链完整。**
> “id=273 ComfyUI中文整合版：精标，README 明确写视频工作流，更新时间 1 天前，下载 21369；短板是镜像近 20GB。”

有角标、有时间、有下载量、有 README 证据、有短板——这才是我们要的理由。

**反例：模型自作主张。**
> “建议直接部署 4090D，约 ¥1.8/时。”

问题：本阶段不部署、不选卡。prompt 里明确写了“最终决定由用户做出，不要写建议直接部署”。

## 六、换一个预设标题怎么改

1. 直接换命令行参数：`python select_apps.py "图像生成" 5`、`python select_apps.py "TTS语音合成" 5`；
2. 如果新标题容易被误判（比如“语音”），在 `prompts/select_system.md` 第四节“主题匹配”里补一句针对该标题的反例：
   “标题是语音时，只把 TTS / 声音克隆类应用算作匹配，不要把训练框架算进来”；
3. 要改陈旧标准就改 `AUTODL_ART_STALE_DAYS`，不要改 `select_apps.py` 的兜底逻辑；
4. 改完重新跑 `select_apps.py`，对比新旧 `llm_raw_<标题>.txt` 确认模型真的按新标准回答了。

## 七、常见坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 返回带 ```json 代码块 | 模型没遵守纯 JSON 要求 | 脚本已自动剥掉代码块；若仍失败看原文并强调格式 |
| 返回的对象里 selected 是空数组 | 模型认为没有匹配项 | 脚本会按收藏数兜底并标 `fallback`，重点看 `summary` |
| 分数都接近 10、理由空泛 | 提示词缺少“必须指出短板/必须带数值” | 已在 `prompts/select_system.md` 第三节加硬要求，再检查原文 |
| 候选明显不相关 | 只抓了列表字段没抓详情 | 先跑 `fetch_details.py 30`，摘要里才会带 README 证据 |
| 明明很旧的应用还进了候选 | 陈旧闸门没生效 | 确认 `update_age_days` 超过 `STALE_DAYS` 的应用确实被 `select_apps.py` 剔除 |
| 「精」标没起作用 | 摘要里没有 `badge` 字段 | 确认 `build_app_summary()` 输出了 `badge`，且 prompt 第 3 条还在 |
