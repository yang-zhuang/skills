# 需求怎么写 & 筛选标准的设计依据

## 一、需求是唯一的"查询条件"

本 skill 的输入就是一句话。模型按你话里的**可判定条件**逐条核对应用资料，所以条件越具体，筛选越准：

| 需求 | 可判定条件 | 预期效果 |
|---|---|---|
| `文生视频，3090 能跑` | 用途=文生视频；显存≤24G | 排掉需要 A100/H800 的应用 |
| `中文 TTS 语音克隆` | 语言=中文；能力=克隆 | 排掉纯英文 TTS、纯配音 |
| `ComfyUI 电商产品图工作流` | 载体=ComfyUI；场景=电商产品图 | 精准到工作流类型 |
| `找好用的` | **无** | 只能按热度兜底，等于没筛 |

正反例总结：
- ✅ 用途 + 约束（硬件/语言/场景/排除项）——「图生 3D，系统盘 30G 装得下」
- ❌ 太泛——「视频」「AI」
- ❌ 太多矛盾条件——「又要显存小又要画质最高」，模型会在 summary 里说明无法两全

## 二、为什么筛选标准大部分在代码里，小部分在 prompt 里

**代码强制的（模型骗不了）**：
- 陈旧闸门：应用级 `updated_at` 超过 `STALE_DAYS`（默认 180 天）的**在调用大模型之前就剔除**，
  名单写进 `selection_*.json` 的 `excluded_stale`；超过 `AGING_DAYS`（默认 90 天）未剔除的应用要求理由提示"维护偏旧"。
- 「精/热」badge：`popular_type` 为 `excellent`→精、`hot`→热（证据：前端 `app-item.js` 的三元表达式），
  作为字段发给模型，并规定只是同档加分项。
- 更新时间：取应用级 `updated_at`（UI 显示的就是它），列表缺这个字段时从版本时间推算并标注来源。
- 数值证据：下载量/收藏数/运行时长原样发过去，要求理由里带真实数值，事后可抽查核对。

**prompt 约束的（模型自己权衡）**：
- 需求匹配优先于一切：badge、热度都不能让"不满足需求"的应用翻盘。
- 开箱程度、硬件可行性这些需要读 README 判断的事。

## 三、模型的输出契约

只输出一个 JSON：`{"selected":[{application_id, name, score, reason}], "summary"}`。
脚本做四道校验：抠 JSON（容忍 ```json 包裹）→ 校验 id 存在于候选池 → 去重 → 数量不足时按收藏数兜底
（兜底的条目标 `fallback: true`，报告里注明"非模型判断"）。原文存 `llm_raw_<需求>.txt`，
模型胡说时直接看原文定位。

## 四、详情覆盖率决定筛选质量上限

- 只抓 30/243 详情时，其余 213 个只有列表字段（名称、简介、热度），**没有 README 证据**；
  模型对它们的判断只基于名字和简介，脚本和报告都会明确标注。
- 要严格筛选全部应用：`python fetch_details.py 0`（约 4~10 分钟）后再 `select_apps.py`。
- 建议：先粗筛（30 详情）看候选格局，锁定范围后再补详情精筛。
