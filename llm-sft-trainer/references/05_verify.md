# 05 · 验收：怎么判断训好了，坏了怎么查

> **这篇管"坏了怎么查"，不管"怎么量"。**
> 速度怎么测、精度分几层 —— `10_measure.md`；多少算够 —— `11_scope.md`；
> 该省显存还是省时间 —— `12_tradeoff.md`。
> 先按那三篇拿到四个数，再看这篇的诊断树。

## 一、四个指标，缺一不可

| 指标 | 从哪来 | 说明什么 | 定义与坑 |
|---|---|---|---|
| train loss | 训练日志 | 有没有在学 | `10_measure.md` 2.1（**不能跨配置比**） |
| eval loss | 验证集 | 有没有学过头 | `10_measure.md` 2.2 |
| tokens/s + 峰值显存 | 日志 / smoke test | 成本是否可接受 | `10_measure.md` 1.2（**1 步测速高估 3 倍**） |
| 探针集指标 | 第 1 步定好的口径 | **任务有没有真的变好** | `10_measure.md` 2.3（判分规则五种写法） |

前三个是过程指标，第四个才是目的。**只有 loss 下降、任务指标不动，等于白训。**

四层证据怎么交叉判读（哪层涨、哪层不涨说明什么），见 `10_measure.md` 2.5 的判读表。

## 二、和 base 对比（必做）

同一批 prompt（至少 10 条，覆盖简单/中等/困难），分别喂 base 和 tuned：

```python
# 伪代码，具体接口看 docs/<lib>/INDEX.md
for p in probes:
    print("BASE  :", generate(base_model, p))
    print("TUNED :", generate(tuned_model, p))
```

看三件事：

1. **该学会的学会了吗**（格式、风格、任务完成度）
2. **不该丢的丢了吗**（通用问答、拒答能力是否退化）
3. **有没有新毛病**（重复、截断、幻觉变多）

**逐条对比，专门盯 "base 对、tuned 错" 的条目**——那是最有价值的信号，
说明模型不是没学到，是**学过头把原有能力覆盖了**（诊断见第三节第 5 支）。
只看总分会把它平均掉：实测出现过 base 8/24 → tuned 18/24，看着涨了 10 条，
但里面有 2 条是退步的。

### 2.1 对比前必须先对齐推理配置（thinking 是最大的坑）

**base 和 tuned 如果不是同一套推理设置，这个对比就不成立。**

实测（Qwen3-0.6B，24 条探针，2026-11-16）：

| | base | tuned | 说明 |
|---|---|---|---|
| 开了 thinking（默认） | **0.0%** | 58.3% | base 每条都在"思考"里打转，350+ 字，答案没写完就被 `max_new_tokens` 截断 |
| 剥离 think 后重算 | **0.0%** | 58.3% | 结论不变 |

看起来是"提升 58.3 个点"，实际上是两个模型在**不同推理配置**下比：

```
base ：真思考 → 写不完 → 0 分
tuned：学成了"空 think + 直接套模板" → 42 字 → 过关
```

**这次训练真正学到的是"把思考关掉了"，不是"学会了任务"。** 提升里有一部分是格式适应，
不是能力。不排除这种情况，你会把一个"变笨了但更听话"的模型当成成功。

**规矩**：

| 做法 | 适用 |
|---|---|
| 两边都 `enable_thinking=False` | 数据里没有 think 标签时的默认选择 |
| 两边都开，且 `max_new_tokens` 给足 | 要保留思考能力时；base 至少要能写完思考 |
| 报告里写明用的哪一种 | 不然下次没人能复现你的分数 |

**判断有没有踩坑**：看 base 的原始输出。如果它是一大段"好的，用户需要我……"，
说明它在思考而不是在回答——**这时候的 base 分数没有意义**。

## 三、诊断树：效果不好，按顺序查

不要一上来就"再训几轮"。按这个顺序，每一层都有明确的检查动作：

### 1. loss 完全不降

| 检查 | 怎么查 | 结论 |
|---|---|---|
| labels 是不是全是 -100 | 打印一条 tokenized 样本的 `labels` | 是 → label mask 配错了 |
| 数据是不是只有一种样本 | `check_dataset.py` 看分布 | 是 → 数据太单一 |
| lr 是不是太小 | 看日志梯度范数 | 是 → 加大 lr |
| chat template 对不对 | 手工 decode 一条样本 | 不对 → 模板没套上 |
| 模型是不是被冻住了 | 打印 `requires_grad` 为 True 的参数名 | 全 False → LoRA 没挂上 |

### 2. loss 降了，但推理效果差

| 检查 | 结论 |
|---|---|
| 训练和推理用的 chat template 是否一致 | 不一致 → 训练白做 |
| 推理时有没有真的加载 adapter | 没加载 → 用的是 base |
| 训练数据分布和真实使用场景差多远 | 差太远 → 数据问题，不是训练问题 |
| eval loss 是否已经回升 | 回升 → 过拟合，减 epoch |

### 3. 输出重复 / 停不下来 / 被截断

| 现象 | 原因 |
|---|---|
| 一直重复同一句 | 训练样本缺 EOS；或 `repetition_penalty` 没设 |
| 话说一半断了 | `max_new_tokens` 太小；或训练样本被截断 |
| 输出空 | `eos_token` 位置不对；或 prompt 模板多了特殊 token |
| 输出固定乱码（如 `{"status = 190/ / / ...`） | **先查是不是忘了 `model.eval()`**，见下面 3.1 |

### 3.1 输出固定乱码：先分清"模型坏了"还是"评测坏了"

实测症状（`Qwen3.5-2B`，LoRA 20 步）：训练后生成
`{"status = 190/ / / / / / ...`，换 lr（2e-4 / 1e-4）、开不开 `assistant_only_loss`
都是同一串；loss 还降到了 0.05，看起来"训得很好"。

按这四步隔离，**别一上来就重训**：

| 步骤 | 做法 | 若正常说明 |
|---|---|---|
| 1 | 基座直接 generate | 环境、tokenizer、chat template 都没问题 |
| 2 | 基座 + 零初始化 LoRA（`get_peft_model` 后直接 generate） | PeftModel 包装没问题 |
| 3 | 训练后换一个重新 `from_pretrained` 的 processor | 不是"模板被训练改掉了" |
| 4 | 训练后在**训练样本自己**身上 generate | 权重没被训坏，问题在数据/泛化 |

本机实测 1/2/3 全正常，第 4 步也正常——**根因是生成前没调 `model.eval()`**。
Qwen3.5 这类混合线性注意力模型，训练模式和推理模式走的是不同实现路径，
停在 train 模式调 `generate` 会输出乱码。

**正例**

```python
trainer.train()
trainer.model.eval()          # ← 手写 generate 前必须加
outputs = trainer.model.generate(...)
```

`trainer.evaluate()` / `trainer.predict()` 内部会自动切 eval，手写循环不会。
这也是"loss 好看 ≠ 模型可用"的典型：训练目标对了，评测代码错了。

### 4. 通用能力明显退化

| 原因 | 处理 |
|---|---|
| 数据太窄，只覆盖一个任务 | 掺 10~20% 通用数据 |
| epoch 太多 | 减到 1~2 |
| lr 太大 | 降一半 |

### 5. 整体提升，但某些样本/类别反而退步

**这一支最容易漏**，因为它不表现为"效果差"，而表现为"效果还行但有几条更糟了"。

实测（`_e2e/05_eval_report.md`，24 条探针）：base 8/24 → tuned 18/24，
**整体涨 10 条**；但困难样本里 2 条 base 对、tuned 错。这不是"没学会"，是**学过头了**。

| 特征 | 原因 | 处理 |
|---|---|---|
| 简单样本全对，困难样本退步 | 数据里简单样本占比高，模型学到"套模板" | 补困难样本；或按难度分层加权 |
| 训练集上对，探针集上错 | 过拟合 | 减 epoch（3→1），或加数据 |
| tuned 输出比 base 更"自信地错" | lr 太大，覆盖了原有能力 | 降 lr 一半，重训 |
| 某一类标签系统性错（如 urgency 恒定 low） | 该类样本太少，模型退化成多数类 | 看标签分布，补齐少数类 |

**判断方法**：把探针**按难度/类别分层**，分别算准确率。
只看总分，会把"简单涨 10 条、困难跌 2 条"平均成"涨了 8 条"，问题被平均数掩盖。

```bash
# 探针集至少要能按这两维分组，否则诊断不了
# 简单 / 中等 / 困难     ← 第 1 步建探针集时就该标好
# 按标签类别（如 intent / urgency）
```

## 六、不达标时回哪一步，改什么

**七步不是单向流水线。** 第 7 步的结果要能倒推回前面某一步，否则就是
"跑完了、结果不好、然后不知道干什么"——这是最常见的卡死点。

第 3、4 节的诊断树只回答"是什么原因"，这一节回答"**所以回去改哪里**"。

| 诊断结论 | 回到 | 改什么 | 改完怎么验证 |
|---|---|---|---|
| label mask 配错、labels 全 -100 | **第 4 步** | 修 mask / 重转数据 | 打印一条 tokenized 样本的 `labels`，看 prompt 段是否为 -100 |
| 训练样本太少、分布单一 | **第 4 步** | 补数据（至少 500 条起） | `check_dataset.py` 看长度和类别分布 |
| 数据分布与真实用法差太远 | **第 4 步**；若任务定义也错了 → **第 1 步** | 重定采集口径 | 人工抽检 20 条，看是否像真实输入 |
| 训练/推理 chat template 不一致 | **第 5 步** | 统一模板 | 同一 prompt 分别走训练和推理的 encode，比对 token id |
| lr / epoch / batch 不合适 | **第 5 步** | **一次只改一个** | 重跑 smoke（≥10 步）→ 通过再全量 |
| 模型太小，能力上限不够 | **第 3 步** | 换更大的模型，或放宽精度档位 | 回第 2 步重新估显存 |
| 目标本身定得不可能达到 | **第 1 步** | 重定 `Q_min`：要么补数据/换模型，要么降标准 | 用 base 的成绩当参照，重写区间 |

**每次只回去一步，只改一个变量。** 同时改两处，下一轮就不知道是哪一处起的作用
（`09_real_cases.md` 案例 13 就是这么来的：两把尺子混用，结论不成立）。

### 迭代预算：不设上限就会无限循环

```
同一个问题最多来回 3 轮
3 轮仍不达标 → 停下来问人
```

因为到第 3 轮还不达标，多半不是调参能解决的，而是**数据或任务定义**层面的问题：

- 数据本身学不出这个能力（标注噪声大、覆盖不全）
- 目标互相冲突（既要准确率 95%，又要训练 10 分钟）
- 探针集有问题（判分规则有歧义，人或模型都对不齐）

每轮必须在 `05_eval_report.md` 里记一行：

```
第 N 轮｜改了什么｜指标从 X 到 Y｜结论
```

**连续两轮指标没动，立即停止调参，回去查数据。** 这是最省钱的止损线。

## 七、什么时候该停

| 情况 | 建议 |
|---|---|
| 指标达标 | 停，交付 |
| 指标差 5% 以内 | 调 lr / epoch 再跑一版，别大改 |
| 指标差很远，且数据检查没问题 | 回头改数据或改任务定义，别继续加算力 |
| 只有 loss 好看，任务指标不动 | 数据或评测口径错了，先修这个 |
| **指标达标，但成本超了预期** | 按 `12_tradeoff.md` 第三节换杠杆，**从第 1 项（换小模型）开始试**，别先调 lr |
| **精度超出区间上限** | 也是问题：方案过配，回去降档（换更省的手段，前提是仍在档内） |
| **为了档内 10% 的差异继续折腾** | 停。档内等价，省下的是别人感知不到的东西（见 `11_scope.md` 第四节） |

最后一条容易被忽略：**精度超出区间上限，和达不到下限一样是浪费**。
85% 的线做到 92%，多出来的 7 个点没有任何业务价值，但成本可能翻倍。
