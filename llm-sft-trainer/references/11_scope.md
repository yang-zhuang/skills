# 11 · 可接受多少：区间、现实、三个维度

> **这篇只管"多少算够"。**
> 怎么把数测出来在 `10_measure.md`；知道卡在哪个维度之后怎么选方案在 `12_tradeoff.md`。
>
> 读完这篇，你应该能回答三个问题：
> 我的可接受范围是**一段多宽的区间**？我**属于哪类现实**？我**唯一卡住**的是哪一个？

## 一、可接受是区间，不是下限

新手（和写这篇的第一版的我）会写成 `精度 ≥ 85%`、`时间 ≥ 5 小时`——
这是一条**线**，隐含了"越往上越好"。于是 4.5 天和 5 天会被排出优劣，10 分钟和 15 分钟也会。

**但人不是这么感知的。**

```
        不可接受          │←────── 可接受区间 ──────→│        浪费
   ─────────────────────┼──────────────────────────┼──────────────────→
        低于下限                             高于上限
        （淘汰）                          （等价，不再比较）  （无效投入）
```

- **低于下限**：不能交付，淘汰
- **落在区间内**：**全部等价**。10 分钟和 15 分钟没有优劣，4.5 天和 5 天也没有
- **高于上限**：多出来的部分不产生任何价值，和达不到一样是浪费

**"区间内等价"是这篇最重要的一句话。**
它直接推出一个反直觉结论：**区间内不存在"最优"，因为都等价。**
在区间内做优化，是把时间花在别人感知不到的地方。

> **术语**：下文把区间里的一段叫「**档**」，跨出区间的边界叫「**跨档**」，
> 和"台阶"说的是同一件事——人感知到的是**一档一档的跳变**，不是连续的百分比。
> "快 10%""准 1 个点"这种说法，只有在**刚好跨过一档**时才有意义。

**注意"等价"的前提**：等价的是**人的感受**，不是机器成本。
4.5 天和 5 天对"等结果的人"等价，但对**这台机器**不等价——它多占了 0.5 天的资源。
所以等价只在"机器不冲突"时成立，见第三节的时间表。

## 二、先看清你的现实：能动的选项有几个

**这一步不能跳。** 不同现实下，"选方案"的空间差一个数量级，
拿"可以换模型、可以多卡、可以租 8 张卡并行试"的思路去做一张 8G 卡上的事，全是废话。

| 现实 | 典型场景 | 模型能换？ | 卡能换？ | 能跑几轮 | 真正能动的 |
|---|---|---|---|---|---|
| **A 小机器，边开发边训** | 笔记本 / WSL / 单卡 8~24G | 多半已指定 | 不能 | **1~2 轮** | 只有开关：QLoRA / ckpt / packing / batch |
| B 专用机，可挂数天 | 单卡 24~80G，非主力机 | 可以，小幅 | 不能 | 3~5 轮 | ＋模型大小、数据量 |
| C 有预算 | 云卡按小时 | 可以 | 可以 | 多轮 | ＋多卡、并行试错 |

**大多数人是 A。** 所以下面默认按 A 写，B/C 的额外空间自己往上加。

**A 类现实最硬的一条：你只有 1~2 次机会。**
跑一轮几小时，你没有"三档都试一遍再挑"的余地。
这一条推翻了所有"扫参""对比实验"的教科书流程——**你必须一次就对**。

所以 A 类的重心不是"怎么选最优"，而是"**怎么让第一次大概率不废**"：
smoke test 一次（几分钟），比跑完 6 小时发现 OOM 值太多。

## 三、三个维度：量出来，不是问出来

理想流程是"问产品经理要数字"。现实里常常没人可问，问了也是"你看着办"。
那就用**能从机器和自己身上直接量到的**东西。

### 3.1 显存——唯一没有商量余地的硬顶

```bash
nvidia-smi                    # 总显存
nvidia-smi --query-gpu=memory.used --format=csv   # 当前已占用（桌面/浏览器/别的进程）
# 你能用 = 总量 − 已占用 − 系统预留
```

不是"24G 卡就能用 24G"。Windows 桌面 + 浏览器 + WSL 自身会吃掉 1~3 GB。
**按实测可用量算，不按型号算。**

### 3.2 时间——你现实中会怎么等

| 你的等待方式 | 上限 | 隐含代价 |
|---|---|---|
| 边写代码边等 | ~30 分钟 | 超过就分心，两件事都做不好 |
| 吃个饭回来 | ~2 小时 | 机器占着，干不了别的 |
| 睡前挂着，早上看 | ~8 小时 | **不能休眠**（笔记本合盖就断，WSL 会停） |
| 挂着过夜 + 白天 | ~24 小时 | 这一天你用不了这台机器 |
| 挂几天 | 数天 | **只有这台不是你的主力机才行** |

**最后一行就是"5 天 vs 4.5 天"的关键前提**——

- 这台机器这 5 天本来也闲着 → 4.5 和 5 确实差不多，别为它优化
- 这台机器是你的开发机 → **每省一天都是实打实能干活的一天**，差别很大

所以"差不多"不是普适结论，**先确认你的机器闲不闲**。
同一个数字，在两种处境下的价值完全不同。

### 3.3 精度——现实里没有下游流程，就用 base 当尺子

现实里很少有人说得出"错 5 条以内可以上线"。更常见的是——**"先跑出来看看"**。

那就这么做（这是现实中最常用的方法，比拍数字可靠）：

```
1. base 模型跑 20 条真实样本 → 记录它错几条、错成什么样
2. 训练后跑同样 20 条
3. 只判两件事：
   ├── 是不是明显比 base 好（好到你一眼能看出来，不用算）
   └── 错的那几条，你能不能人工兜住
```

**这就是"用基线定义范围"**，而不是先定一个抽象数字。

为什么比"定 95%"现实：
- 你手上根本没有"业务要求"这种东西
- base 的水平是**现成的、真实的参照**
- "从 62% 提到 85%"可验证；"做到 95%"是许愿

**如果能问到人**（有产品/客户/上级），按这个顺序问，越靠前越可靠：

| 问法 | 得到的 | 可靠性 |
|---|---|---|
| "错了会怎样？谁去处理？" | 要全检 → 精度必须很高 | 最高（直接对应人力） |
| "不能比现在这版差吧？" | ≥ 现版本 − 1 点 | 高（有基线） |
| "base 太差，得提到能用" | 相对提升幅度 | 中（幅度是估的，方向对） |
| "做到 90% 吧" | 90% | 最低，但比没有强 |

## 四、优化只发生在"跨档"的时候

| 情况 | 该做什么 |
|---|---|
| 两个方案在同一个档内 | **停止优化**，选实现简单的那个 |
| 差一点跨不过档 | 优化，目标是**跨过去**，不是"更好" |
| 已经在上一个档，跨下一个代价很大 | 停，交付 |

**实例（A 类现实）**：

| 场景 | 判断 |
|---|---|
| 笔记本上 3.2 小时 → 2.9 小时 | 都是"一下午"，**别折腾**，这 20 分钟换不来任何事 |
| 6 小时 → 2.5 小时 | 从"挂一夜"变成"一下午能跑完还能再改一版"，**值得做** |
| 5 天 → 4.5 天（专用机） | 机器闲着，**别折腾** |
| 5 天 → 4.5 天（主力开发机） | 省出半天能干活，**看这半天对你值不值** |

**"5 天 vs 4.5 天"还有第二层原因**（不只是"数值接近"）：
当你的目标是省显存时，时间根本不是目标维度，**连比较的资格都没有**。见 `12_tradeoff.md` 第一节。

**A 类现实还有一个额外约束**：你只有 1~2 次机会。
所以这里的优化不是"追最优"，而是"**保证这一次不废**"——
宁可要一个在档内、但你已经验证过能跑通的方案，
也不要一个理论上更快、但你没时间验证的方案。

## 五、三个区间，只有一个需要动

```
精度：[Q_min, Q_max]     低于 Q_min 不能交，高于 Q_max 是无效投入
时间：[S_min, S_max]     超过 S_max 等不起，快于 S_min 没有额外价值
显存：≤ M_max            物理硬顶，超了直接 OOM（没有"下限"这回事）
```

**通常只有一个区间是真的卡住的**，其余两个你都宽裕。先找它。

**实例（A 类现实：2B 模型已指定、8G 卡实际可用 7.2G、一个下午 4 小时）**

> 8G / 7.2G / 4 小时都是**举的例子**，换成你自己 `nvidia-smi` 和 3.2 表里的数。

| 配置 | 峰值显存 | 时长 | 判断 |
|---|---|---|---|
| seq=1024 + LoRA | 4566 MiB（实测） | 3.20 s/step | 显存够 → **用 LoRA，别上 QLoRA** |
| seq=1024 + QLoRA | 3220 MiB（实测） | 3.68 s/step | 省了 1.3G，但你本来就不缺 → **纯亏 15% 时间** |
| seq=4096 + LoRA | 激活涨约 4 倍，逼近硬顶 | 更慢 | **这时显存才卡住** → 换 QLoRA |
| 全参 | 远超凡存 | — | 出局 |

**这张表说明一件容易被忽略的事**：卡住你的约束**会随参数变化**。
seq=1024 时你卡的是时间（想快点出结果），seq=4096 时你卡的是显存（装不下）。
所以"该用 QLoRA 还是 LoRA"没有固定答案——**取决于你当前在哪一档，卡的是哪一个**。

- seq=1024：三个都在档内 → **不需要优化，选实现最简单的**
- seq=4096：显存卡住 → 只有一条路：上省显存的手段（`12_tradeoff.md` 第二节）
- 显存够却还上 QLoRA：**这是最常见的错误**，用 15% 的速度买了一个你不需要的东西

**如果你的项目天生就是显存紧张型**（模型大、序列长、多卡才装得下），
那你不用纠结——**你开局就在省显存那张表里**，直接按它从上往下试。
这张对照表是给"显存够、但总觉得自己该上 QLoRA"的人看的。

**判断口诀**：**找出唯一卡住的那个区间，只动它。另外两个在档内就别管，那不是你的战场。**
