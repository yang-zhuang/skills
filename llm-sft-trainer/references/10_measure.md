# 10 · 度量：速度怎么测、精度怎么评

> **这篇只管"怎么拿到数"。**
> 拿到数之后"多少算够"在 `11_scope.md`，"该省显存还是省时间、选哪个方案"在 `12_tradeoff.md`，
> 把三篇串起来练一遍在 `13_practice.md`。
>
> 读完这篇，你手上应该有**四个数**。没有这四个数，后面两篇都做不了。

## 0. 四个数，各有各的坑

| 数 | 从哪来 | 回答什么 | 最容易错在哪 |
|---|---|---|---|
| `train_loss` | 训练日志 | 模型有没有在拟合 | **不能跨配置比**（分母会变） |
| `eval_loss` 曲线 | 验证集 | 什么时候该停 | 只能判过拟合，判不了好坏 |
| **探针分** | 你自建的 20~50 条 | 任务到底做对没有 | 判分规则写松了，分数虚高 |
| **s/step + 峰值显存** | 日志 / smoke test | 要跑多久、装不装得下 | 用 1 步测速，高估 3 倍 |

**前两个免费，第三个要写判分，第四个只要跑 20 步。** 四个都齐了才算"量过"。

> 名词先对齐：**速度**是单位时间处理多少 token（可换算成时长和钱）；
> **精度**是任务做对的比例（**不是 loss**）。
> 把 loss 当精度，会训练出一个 loss 0.05 但输出乱码的模型（`05_verify.md` 3.1）。

## 一、速度：三层，每层都能复算

### 1.1 公式与量纲

速度不是一个数，是一条链。**每一层都能从上一层算出来**，算不出来就说明你缺数据。

```
第 1 层  step/s        = 1 / 每步秒数
第 2 层  tokens/s      = 每步 token 数 × step/s
第 3 层  GPU-hours     = 总 token 数 / tokens/s / 3600 × 卡数
第 4 层  钱（¥）        = GPU-hours × 单价
```

其中 **每步 token 数** 是最容易搞错的一项：

```
每步 token 数 = per_device_bs × grad_accum × 卡数 × seq_len
```

这是**名义值（上界）**——它把 padding 的空位也算进去了。
真实有效值要靠 `check_dataset.py` 统计出来的实际 token 数，两者可能差 2~4 倍。

**量纲检查法**（自查有没有算错，一行就能验证）：

```
step/s × 总步数        = 总秒数         ✓
samples/s × 总秒数     ≈ 样本数         ✓
tokens/s × 总秒数      ≈ 总 token 数    ✓
```

对不上就是公式用错了。这不是玄学，是单位。

### 1.2 测哪个窗口：本机实测，差 4 倍

**这是新手最容易踩的坑，比参数名写错还常见。**

同一台机器、同一个模型（Qwen3.5-2B，bf16 LoRA，bs=1×accum=4，seq=1024），
只是训练的步数不同：

| 跑了多少步 | `train_runtime` | 折算 s/step | 由此预测「1 万条 × 3 epoch」 |
|---|---|---|---|
| **1 步** | 13.45 s | 13.45 | **28.0 小时** |
| **2 步** | 13.50 s | 6.75 | 14.1 小时 |
| **20 步** | 64.07 s | **3.20** | **6.7 小时** |

（数据：`sft-case/out/result-fail-mask.json`、`result-probe2.json`、`result-lora-bf16.json`）

**同一份代码，用 1 步测出来的速度比真实值高估 320%**，预测总时长从 6.7 小时变成 28 小时。
如果你按 28 小时去申请资源，会多要 4 倍；如果按它判断"这个方案跑不起"，会否掉一个其实能跑的方案。

为什么：第 1 步里塞了 cudnn benchmark、triton kernel 编译、显存池首次分配、数据加载器预热。
这些是**一次性开销**，摊到 20 步里就只剩 0.6 秒，摊到 1 步里就是 10 秒。

**规矩**：

```
测速至少跑 10 步，且丢掉前 2 步，取后面的中位数
```

10 步以下的数字，只能用来判断"会不会 OOM"，**不能用来估时长**。

### 1.3 口径必须统一（这次真的被绊了一下）

上表用的是 `train_runtime`（Trainer 内部计时）。
同一个实验里还有另一个数：**你自己在脚本外面掐的表**（`train_seconds`，含建 trainer、存 ckpt、收尾）。

本机实测，同一个 run：

| 口径 | 20 步 | 折 s/step |
|---|---|---|
| `train_runtime`（Trainer 内部） | 64.07 s | 3.20 |
| `train_seconds`（脚本外部） | 64.36 s | 3.22 |

差 0.5%，看起来无所谓。**但我在写这篇时，1 步用了 `train_runtime`、20 步用了 `train_seconds`，
算出来 318%；统一口径后是 320%**——两个"看起来都对"的数，谁也对不上。

**规则**：

- 表里的每一行必须来自**同一个字段**，并在表头注明是哪个；
- 推荐全用 `train_runtime`：它排除了模型加载、checkpoint 保存、进程启动，只算训练本身；
- 换字段就等于换尺子。尺子换了，前后两个数不能相减。

（这条错误的完整经过见 `09_real_cases.md` 案例 13。）

### 1.4 三个库的字段名（同源，但展示不同）

三库底层都是 transformers `Trainer`，所以**最终汇总字段是同一套**：

| 字段 | 含义 | trl | unsloth | ms-swift |
|---|---|---|---|---|
| `train_runtime` | 总训练秒数 | ✓ | ✓ | ✓ |
| `train_samples_per_second` | 样本吞吐 | ✓ | ✓ | ✓ |
| `train_steps_per_second` | 步吞吐 | ✓ | ✓ | ✓ |
| `train_loss` | 全程平均 loss | ✓ | ✓ | ✓ |
| 实时进度 | 每 N 步一行 | ✓ | ✓ | `train_speed(iter/s)` + `memory(GiB)` + `remaining_time` |

**swift 多给两样，别浪费**：

```python
{'loss': 1.4406, 'grad_norm': 10.125, 'learning_rate': 2.5e-07, 'token_acc': 0.6267,
 'epoch': 0.91, 'global_step/max_steps': '85/94', 'percentage': '90.43%',
 'elapsed_time': '2m 43s', 'remaining_time': '17s',
 'memory(GiB)': 6.5, 'train_speed(iter/s)': 0.520331}
```

（真实日志见 `docs/swift/BestPractices/Metax-support.md:137`，这是第 85/94 步那一行）

- `memory(GiB)`：**每步的实时显存**，能看出显存随长度增长的趋势，比只看峰值有用
- `token_acc`：token 级准确率，**免费的精度代理指标**，trl/unsloth 没有
- `remaining_time`：swift 自己算好的剩余时间，**可以直接用来核对你的估时**——
  它和你的手算差 2 倍以上，说明你的 s/step 取错了窗口（见 1.2）

**字段名会变**（这就是文档会实时变化的地方）。变了怎么找：

```bash
# 不要背字段名，搜"速度"这个概念词
python scripts/docs_outline.py --search speed
python scripts/docs_outline.py --search throughput
grep -rn "per_second\|train_speed\|tokens_per_s" docs/<lib>/ | head
```

### 1.5 四类"假速度"

看到好得不像话的数字，先排除这四种：

| 现象 | 真实原因 | 怎么识别 |
|---|---|---|
| tokens/s 高得离谱 | 分母是**名义 token**（含 padding） | 用有效 token 重算，通常掉 2~4 倍 |
| 中途突然变慢 | 在存 checkpoint / 跑 eval | 看日志时间戳，周期性掉速就是它 |
| 越训越快 | 短样本先来，长样本后到 | 看 seq_len 分布；开 packing 可缓解 |
| 多卡没加速 | 数据加载成瓶颈（`num_workers` 太小） | GPU 利用率上不去，而 CPU 满载 |

**实测例子（本机，QLoRA vs LoRA，2B 模型）**：

| | LoRA (bf16) | QLoRA (4bit) | 差异 |
|---|---|---|---|
| 峰值显存 | 4566 MiB | 3220 MiB | **−29.5%** |
| 每步耗时 | 3.20 s | 3.68 s | **+14.9%** |
| 20 步后 loss | 0.683 | 0.652 | 差 0.03，**在噪声内，没有判别力** |

**loss 那一行要特别小心**：20 步远没收敛，这点差异证明不了 QLoRA 更好或更差。
同一批实验里，lr 从 2e-4 降到 1e-4，loss 从 0.687 跳到 0.972——
**lr 的影响远大于 LoRA/QLoRA 的差异**。用 20 步的 loss 比精度，是在读噪声。

**这两行数字怎么用**（这是最容易用错的地方）：

- ❌ 错误用法："QLoRA 慢 14.9%，所以不如 LoRA" —— 把买显存的价钱当成了缺点
- ❌ 错误用法："QLoRA 省 29.5%，所以总是更划算" —— 显存够的时候，你买了个用不上的东西
- ✅ 正确用法：**先看你的显存够不够**（`11_scope.md` 第五节）。不够 → 这 29.5% 是救命钱；
  够 → 一分钱都别花，直接用 LoRA

同一组数字，结论取决于你的处境，**不取决于数字本身**。

### 1.6 从速度到成本（这是"钱"这本账，别和另外两本混）

`12_tradeoff.md` 会讲"你在省什么"有三种：显存、时间、钱。**这一节只算钱。**

```python
s_per_step   = 3.20                              # 取自 train_runtime 口径
steps_per_ep = 总样本数 / (bs * grad_accum)      # 10000 / 4 = 2500
total_hours  = s_per_step * steps_per_ep * epochs / 3600   # 3.20*2500*3/3600 = 6.7 h
gpu_hours    = total_hours * 卡数
cost         = gpu_hours * 单价                  # 租卡才需要，本机算时间成本
```

**本机也要算 GPU-hours**，因为你的时间就是成本。
统一成 GPU-hours 之后，本机和租卡才能放在一张表里比。

**但注意**：这个数只回答"这轮要烧多少机器时间"。
它**不能**替你决定"该不该上 QLoRA"——那个只看显存够不够。
**钱、显存、时间是三本账，分开记。**

## 二、精度：四层证据，从免费到贵

精度不是一个数，是**四层证据的交叉验证**。
每一层的成本差一个数量级，能从便宜层拿到结论，就不要往上爬。

| 层 | 成本 | 能证明 | **不能**证明 |
|---|---|---|---|
| L0 train loss | 免费（日志自带） | 模型在拟合 | 任务做对了 |
| L1 eval loss | 便宜（多跑一次验证集） | 有没有过拟合 | 生成质量 |
| L2 探针集 | 中（要写判分） | **任务指标** | 没覆盖到的场景 |
| L3 盲评 | 贵（人工） | 真实可用性 | 统计显著性（样本太少） |

### 2.1 L0 · train loss：只能回答"有没有在学"

**它不能跨配置比较。** 这是硬规则，本机有铁证：

同模型、同数据、同 lr，**只改了 `assistant_only_loss` 一个开关**：

| 配置 | train loss |
|---|---|
| 全序列算 loss | 0.683 |
| 只算 assistant 部分 | **0.0495** |

loss 掉了 93%，但模型没有任何区别——**分母变了**。
只算回答部分时，回答是模板化的 JSON，极其好拟合，loss 自然低。

（`result-mask-on.json` vs `result-lora-bf16.json`，其余参数完全一致）

**能说的**：loss 从 2.5 降到 0.7，说明模型在这个分布上开始拟合了。
**不能说的**：loss 0.05 所以模型很好。
**典型误判**：loss 好看 + 输出乱码 = 评测代码错了，不是模型坏了（见 `05_verify.md` 3.1）。

### 2.2 L1 · eval loss：只回答"有没有学过头"

判据只有一条：**它开始回升了吗**。

```
eval loss 单调下降          → 继续训
eval loss 走平 2 个 eval 点  → 可以停
eval loss 回升              → 过拟合，减 epoch 或加数据
```

**注意**：eval loss 降、生成变差，是完全可能的。原因是对数似然训练的是"平均每个 token 的概率"，
而生成是自回归采样，误差会累积（exposure bias）。
所以 **eval loss 只能用来判断什么时候停，不能用来判断能不能交付**。

### 2.3 L2 · 探针集：唯一能回答"任务做对了没有"

这是第 1 步就该定好的东西，不是第 7 步才想。

**怎么建（20~50 条就够）**：

| 要求 | 做法 | 为什么 |
|---|---|---|
| 分层 | 简单 10 条 / 中等 20 条 / 困难 10 条 | 只看总分会被简单样本掩盖 |
| 不来自训练集 | 从真实场景另取，或训练集留出 | 防止"背下来了" |
| **可自动判分** | 规则明确，能写成代码 | 否则每次评测都要人工，做不了对照 |
| 覆盖边界 | 空输入、超长、格式异常各来 2 条 | 训练集里通常没有 |

**判分规则怎么写**（从便宜到贵，能用上面的不用下面的）：

```python
# 1. 精确匹配：适合分类、抽取、固定格式
score = (pred.strip() == gold.strip())

# 2. 结构化比对：适合 JSON 输出——只比关键字段，忽略空格和顺序
score = json.loads(pred) == json.loads(gold)      # 或逐字段比

# 3. 包含匹配：适合长答案，检查必含要点
score = all(k in pred for k in gold_keywords)

# 4. 规则+正则：适合带格式的自由文本
score = bool(re.match(r"^\d+\.\d{2} 元$", pred))

# 5. LLM 判分：只在前四种都做不了时用
#    代价：不可复现、有偏、每次结果可能不同 → 必须固定 prompt 和模型版本
```

**判分规则必须写进 `00_task_profile.md`**，否则第 7 步你会不自觉地"往宽松了判"。

### 2.4 L3 · 盲评：只用来校准 L2，不是日常手段

做法：从探针集抽 10~15 条，**不告诉评审哪条是 base、哪条是 tuned**，让他排序。

用途只有两个：
1. 校准探针集——如果 L2 说 85% 但盲评觉得"一半不能用"，说明判分规则太松
2. 发现新毛病——重复、啰嗦、幻觉，这些规则判不出来

**不要每次训练都盲评**，那是在用最贵的手段做最便宜的判断。

### 2.5 交叉判读：哪层涨哪层不涨，说明什么

**这张表是这一节的全部价值**——单看一个指标永远不知道错在哪，四个一起看才能定位。

| L0 loss | L1 eval | L2 探针 | L3 盲评 | 结论 |
|---|---|---|---|---|
| ↓ | ↓ | ↑ | 好 | 正常，可交付 |
| ↓ | 回升 | 不动 | — | 过拟合，减 epoch |
| ↓ | ↓ | 不动 | — | **训练目标 ≠ 任务目标**，检查数据格式/chat template |
| ↓ | ↓ | ↑ | 差 | 探针集太简单或有泄漏，重建探针集 |
| 不降 | — | — | — | 见 `05_verify.md` 诊断树第 1 层 |
| 极低 | — | 差 | 输出乱码 | 大概率是 `model.eval()` 没调，不是模型问题 |

**最后一行是真事**：`result-eval-fix.json` 里 loss 0.68、输出正常；
另一版 loss 0.05、输出 `{"status = 190/ / /`——差别只在生成前有没有 `model.eval()`。

## 三、度量就是回归测试：文档变了怎么发现

文档会实时变化：参数改名、默认值改了、推荐做法换了、示例里的数字过时了。
**光靠重跑索引发现不了"结论失效"**——页面还在，只是说的不一样了。

| 变化类型 | 例子 | 怎么发现 | 怎么应对 |
|---|---|---|---|
| **索引层**（页面增删改名） | 目录重组、25 页迁移 | `--recipes` 出 `MISS` | 按 `06_docs_nav.md` 的心法重跑 |
| **口径层**（参数/字段改名） | `--train_type` → `--tuner_type` | 运行时 `unrecognized arguments` | 在 `docs/` 里 grep 概念词，不背名字 |
| **结论层**（说法变了） | "QLoRA 省 70%" 在你的模型上不成立 | **只有实测能发现** | 跑一次 smoke test，对比历史数字 |

**第三层是最危险的**：前两层会报错，第三层不会。文档说省 70%，你信了，
实际省 29.5%，你的显存预算就错了 40%——**它不报错，只是悄悄地错**。

### 存一组基线数字

```markdown
# 06_metrics_baseline.md（放在训练工作目录）

| 日期 | 模型 | 配置 | s/step | 峰值显存 | 探针分 | 文档版本 |
|---|---|---|---|---|---|---|
| 2026-11-16 | Qwen3.5-2B | LoRA bf16 | 3.20 | 4566 MiB | — | swift@11-16 |
```

**什么时候拿它比对**：升级库版本、换驱动/CUDA/torch、重同步文档发现有改动、换机器。

**判定规则**：

```
同一配置，速度或显存变化 > 15%  → 有东西变了，查清再继续
同一配置，loss 曲线形状明显不同  → 训练逻辑变了，不是随机波动
```

**为什么要存"文档版本"一列**：出问题时能回答"当时我是按哪版文档做的"。
用 `docs/*/INDEX.md` 的同步时间，或 `git log` 里 manifest 的提交时间。

### 一条命令做回归

```bash
python scripts/docs_outline.py --recipes --step 7   # 先确认缓存没过期
# 再跑你的 smoke test，把新数字填回基线表
```

**关键心法**：文档是"别人说的"，度量是"你自己测的"。
文档变了，你唯一能信的锚，就是你上次测出来的那组数字。
