# 00 · 总流程与每层的闸门

## 目的

把「训练一个模型」从「打开 trl 文档从第一页读到最后一页」变成**固定顺序的七步**。
每一步都有明确的产出物和通过条件。

**两个方向，别混：**

- **往前**：不通过就停在这一步，不许往后跳（第 2 步没数字，第 3 步就是猜）
- **往回**：第 7 步验收不达标时，**要能倒推回前面某一步**，否则流程只是流水线——
  跑完了、结果不好、然后不知道干什么。回退表在 `05_verify.md` 第六节。

为什么必须固定：不固定的话，每次都会变成「先看看数据？还是先写脚本？还是先查显存？」，
看着很忙，其实在原地打转。

## 七步总览

| 步 | 名字 | 一句话 | 产出物 | 通过条件（gate） |
|---|---|---|---|---|
| 1 | 定任务 | 搞清楚要做什么、做到什么算成功、**以及多快算够** | `00_task_profile.md` | 目标、数据来源、评测口径**、速度/成本下限**四样都有 |
| 2 | 探环境 | 卡/显存/库/模型，全部变成数字 | `01_env_report.md` | 有真实显存数字，不是"应该够" |
| 3 | 定方案 | 三档精度 + 上下文目标 + **三库分工与组合** + 候选对比 | `02_training_plan.md`（+ `plan.png`） | 每个决策都有三库对照 + 依据 + 验证方法，并写了"为什么不用另外两条"；**候选 ≥3 个时附选型图和淘汰原因** |
| 4 | 备数据 | 已有就转格式，没有就生成 | `03_dataset_report.md` + 数据文件 | token 分布算出来了，超长比例有结论 |
| 5 | 写脚本 | 按方案和数据生成，先 smoke test | `train.py` + `train.sh` + `config.yaml` | smoke test 跑通、不 OOM、**拿到 ≥10 步的真实速度**；**并把三件套完整交付给用户（见 04_train.md §7）** |
| 6 | 跑训练 | 全量训练 + 记录 | `outputs/` + 训练日志 | 训练正常收敛，没有 NaN |
| 7 | 验收 | 评测 + 诊断 + 部署验证 + **成本核算**；不达标则按回退表往回走 | `05_eval_report.md` | 达到第 1 步定的精度线**和**速度线，且是最廉价的合格方案。**未达标时必须写出回退决策**（回第几步 / 只改哪个变量 / 第几轮） |

只有第 6 步是「等机器跑」；其它六步都是判断。**判断错了，跑再久都是白跑。**

## 训练工作目录长什么样

不要把所有东西堆在技能包里。每次训练开一个新目录：

```
<你的训练工作目录>/
├── 00_task_profile.md        任务与成功标准（第 1 步）
├── 01_env_report.md          环境探测（第 2 步）
├── 02_training_plan.md       方案与依据（第 3 步）
├── 03_dataset_report.md      数据体检（第 4 步）
├── data/                     转换后的训练数据
├── train.py                  训练主体（smoke/full 共用这一份）
├── train.sh                  启动脚本（smoke / full 两模式）
├── config.yaml               超参（和代码分开，方便做对照）
├── outputs/                  检查点与日志
└── 05_eval_report.md         评测与诊断（第 7 步）
```

技能包只提供**流程、脚本、文档**；训练产物留在工作目录。这样换模型、换任务互不污染。

**第 5 步的三件套可以直接从 `templates/` 复制起步**（`train.py` / `train.sh` /
`config.example.yaml`），它是实测跑通的版本泛化来的。但"复制"不是终点：
按你的模型、数据格式、显存把 config 改对，并读懂 `train.py` 里标出的精华和坑
（见 `04_train.md`）。**实战结束时，必须把这三份脚本完整交付给用户**——
脚本写在磁盘上不等于交付，用户看到、拿到、能改才算（见 `04_train.md` §7）。

## 四条不许破的规矩

1. **数字必须是测出来的**。"这个模型 7B 应该能全参"不算，`probe_model.py` 算一遍、
   smoke test 跑一遍才算。
2. **一次只改一个变量**。改学习率的同时又改 seq_len，效果变好你也不知道是谁的功劳。
3. **文档说的不算**。文档写"支持 128k"，你的卡不一定支持；必须按 04 的 smoke test 验。
4. **三库必须一起看，再综合**。同一件事 trl / unsloth / swift 各有答案，覆盖范围也不同
   （评测只有 swift 有专章、500k 只有 unsloth 有实测）。只看一个库，会漏掉更简单的路或更高的上限。
   读完给"最简 / 最强 / 怎么组合"，见 `08_cross_lib.md`。

## 什么时候该停下来问人

只有这四种情况值得停下来：

| 情况 | 为什么停 |
|---|---|
| 要下载几十 GB 的模型/数据 | 占磁盘、耗时间，要先让人知道下到哪 |
| 要花超过 1 小时的训练 | 先确认方案，别跑完才发现方向错 |
| 数据来源是"生成"的 | 生成的数据质量没人保证，要人确认 |
| 要动别人的环境/已有服务 | 可能影响别人 |

其余情况自己往下走，不要每一步都等点头——那样这套流程就没有存在意义。

## 第 1 步的任务模板

第 1 步不写清楚，后面全是猜。`00_task_profile.md` 至少要有这五项：

```markdown
# 任务画像

## 1. 要做什么
<一句话，动词开头：把客服对话改写成标准工单 / 让模型学会按 JSON 输出 ...>

## 2. 数据
- 来源：用户提供 / 已有 / 需要生成
- 路径或获取方式：<...>
- 规模：<条数，未知就写未知>

## 3. 基座模型
- 用户指定：<HF id 或本地路径>
- 若未指定：<按什么标准选，见 02_decide.md>

## 4. 硬件
- 卡数与显存：<未知就写未知，第 2 步探测后回填>
- 能否多卡：<是/否/未知>

## 5. 成功标准（写成区间，不是一条线）
- 现实类型：<A 小机器/边开发边训｜B 专用机｜C 有预算> → 决定你能动哪些选项
- 精度区间：<下限：低于它不能交；上限：高于它没有额外价值>
  - 下限从哪来：<base 跑 20 条错几条 → 要比它好多少；或下游后果反推>
- 探针集：<20~50 条，**必须按难度分层：简单/中等/困难**，判分规则怎么写>
  → 分层不是为了好看：**第 7 步要靠它发现"整体涨了但困难样本退步"**，只看总分会把退步平均掉
- 时间档：<你现实中会怎么等：边写代码 30min / 一顿饭 2h / 挂一夜 8h / 挂几天>
- 显存硬顶：<`nvidia-smi` 实测可用量，不是卡型号>
- **唯一卡住的那个**：<精度 / 时间 / 显存，只填一个>
- 次要约束：<如 通用问答退化不超过 5%>

## 6. 明确不做的
- <如 本版不做强化学习、不做多模态>
```

**第 1 步最常见的三个坑**：

1. 只写"训练一个模型"，没写"怎么算成功" → 第 7 步没法验收，只能靠感觉
2. 只定精度，不定时间/显存 → 做出一个达标但塞不进去、或者等不起的方案
3. **把成功标准写成一条线（"越快越好""越准越好"）** → 会在档内做无效优化，
   花一天去省那 20 分钟，而人根本感知不到

第 3 个坑最隐蔽：它不会报错，只会让你**一直很忙但没有进展**。
区间怎么定、什么叫"档内等价"，见 `11_scope.md`。
