# 渲染保真：图渲出来不对时读这个

适用症状：**字发虚 / 字形空心 / 轴号撑破圆圈 / 数字变灰 / 图被挤成一小块 / 小图看不清**。
这些几乎都不是拆分的问题，而是渲染链路上的已知坑。

## 一、SHX 字体：三个目录必须都给上

`SHX_FONT_DIRS`（分号分隔，支持 glob，**顺序即优先级**）：

```ini
SHX_FONT_DIRS=G:\Tangent\TArchT20V9\SYS;C:\Program Files\Autodesk\AutoCAD*\Fonts
```

| 目录 | 里面有什么 | 缺了会怎样 |
|---|---|---|
| 天正 `SYS` | `hztxt.shx`、`tssdchn.shx` 等中文形字体 | 中文退化成 TTF 替身 |
| AutoCAD `Fonts` | `SIMPLEX` / `COMPLEX` / `TXT` / `ROMANS` / `gbcbig.shx` | 数字和字母退化成替身 |

### 两个必须做对的地方

**① 注册顺序**：`ensure_shx_support()` 要在任何文字度量**之前**（即 `build_clusters`
之前 —— 它求 bbox 会触发度量）。原因：ezdxf 的 `_CachedFont._glyph_caches` 是**类级**
字典，先被解析成 TTF 替身就把结果缓存住了，之后再注册 SHX 也不会重算
（`font_manager.clear()` 只清字体管理器，清不掉它）。表现是**字形放大 ~1.27× 且退化为空心轮廓**。

**② 解析顺序**：`ezdxf.options.set("drawing-addon", "shx_resolve_order", "stl")`。
默认是 `"tsl"`（**TrueType 优先**），于是 ezdxf 先挑自带 TTF 替身
（`simplex_.ttf` / `complex_.ttf`…），磁盘上的真 SHX 永远轮不到。后果两条：

- 替身是"单线笔画转出的极细轮廓"，TTF 又走 `draw_filled_paths`（linewidth 硬编码 0）
  → 笔画细成发丝，小字号抗锯齿后一片灰；
- 替身字宽与真 SHX 不同 → 标注间距与原图不一致。

改成 `"stl"` 后 SHX 优先命中，文字走 `draw_path`（描边），`lineweight` 才真正生效。

## 二、为什么同一根 1px 线，白底看着没事、黑底直接看不见

**现象**：轴号 ①②③、尺寸数字 4200 / 29100 发灰发虚，同图的「北」却清晰。

**根因是字体分支不同，与底色、与颜色都无关**：

| 文字类型 | 渲染路径 | 结果 |
|---|---|---|
| 中文/混排 → 换成 `simhei.ttf` | `draw_filled_paths`（fill=True, linewidth=0） | 笔画由字形轮廓决定 → **实心饱满** |
| 纯 ASCII / 拉丁 → 保留 SHX 单线字体 | `draw_path`（fill=False） | 线宽 = 实体有效线宽 0.25mm → 1.04px @300dpi |

1px 的线落在像素网格之间时，抗锯齿把墨量摊到相邻像素 → 中间灰。白底是"黑压白"，
灰边不显眼；黑底是"灰压黑"，**直接读不出来** —— 同一根线在白底被误判为"没问题"。

**解法**：按「字高像素」临时抬高文字的描边线宽，渲染后还原
（`TEXT_STROKE_RATIO = 0.045`，下限 2.5px / 上限 8px）。
**不换字体** —— 换 TTF 会改变字宽，把标注挤错位（TTF 数字比 SHX 宽）。

## 三、图幅自适应：为什么不能靠 dpi 调清晰度

ezdxf 的 `qsave` 默认尺寸由 `plt.figaspect()` 决定 —— **高度锁死 matplotlib 默认的
4.8 英寸**，宽度按长宽比推算。于是"图幅越大、每 DSU 分到的像素越少"：
18300×15250 DSU 的图在 150dpi 下只有 866×720px，尺寸数字只有约 14px 高，笔画不足
1 像素 → 塌成浅灰。

解法是**显式传 `size_inches`**，按「长边目标像素」自适应，并给每 DSU 的像素密度设上限
（避免小图被放大到离谱）：

| 常量 | 值 | 含义 |
|---|---|---|
| `PNG_TARGET_LONG_PX` | 2400 | 单张拆分图的 PNG 长边目标像素 |
| `PNG_MAX_PX_PER_DSU` | 0.5 | 每 DSU 最多放大到 0.5px |
| `PNG_MAX_INCH` | 16.0 | 单边最大英寸（**硬上限 = 16 × dpi**） |
| `PNG_OVERVIEW_LONG_PX` | 4800 | **整图**用。16 英寸 × 300dpi = 4800px 正好是夹取上限 |

⚠️ **提高 `dpi` 不会让像素变多** —— 英寸尺寸由"长边目标像素"反算，最终像素 = 英寸 × dpi，
与 dpi 无关。dpi 只影响同一幅面下的清晰度。要让整图更清晰，改的是
`PNG_OVERVIEW_LONG_PX`，而且**再往上设会被 `PNG_MAX_INCH` 夹回来，白设**。

## 四、剖面线相位必须可复现

ezdxf 画 DXF HATCH 的图案时，`_jiggle_factor()` 会调 `random.random()` 给图案原点加
随机微偏移（0.03%~0.1% 幅面）—— 这是 ezdxf 的刻意设计（避免剖面线正好压在边界线上）。

代价是：Python 的 `random` 每个进程从 OS 熵自动播种 → **同一张图两个进程渲出来不一样**
（剖面线相位差亚像素，边缘抗锯齿差 ±1~6 灰阶；实测 `平面示意图4` 两次独立进程差异
414~627 px）。纯线框图 0 差异，含 PATTERN HATCH 的图才中招。

解法：`RENDER_RANDOM_SEED = 0`，每个变体渲染前都重置 → 同一张图逐字节一致。
**逐像素回归比对才有意义**（否则"差异"分不清是代码改的还是随机相位）。

## 五、两类特殊图元

- **`‰` 倾斜值**：天正原图作者把它画成两个实体（数字 h=1000 + `‰` h=964.5），
  `‰` 位置写死为"数字插入点 + 2000 图形单位"。渲染时按文字重建 `‰` 几何
  （`_PERMILLE_RINGS` / `_PERMILLE_SLASH`），避免字体缺字形导致的基线错位。
  `merge_permille.py` 是把它俩合并成单实体 "0.88‰" 的独立修补工具。
- **零宽段**：LWPOLYLINE 里宽度为 0 的段会产生零面积多边形，渲染器画不出来。
  渲染前临时补偿到「对角线长度的 0.05%」（`_bump_zero_widths`），渲染后还原
  `eps = max(diag * 0.0005, 0.5)`。
- **退化椭圆/弧**（major axis 为 0）：会抛 `invalid major axis: (0,0,0)`，
  **PNG 失败但 DWG 正常导出**。见 `LESSONS.md` 的 L-006。

## 六、排查顺序（别乱试）

1. 先确认**源图导出成天正3（T3）没有** —— 没导出的话下面全是白折腾（程序会在第 0 步
   直接拦下报 `T3RequiredError`，见 README「拆分对象」）；
2. 再确认 `SHX_FONT_DIRS` 三个目录都在、且注册顺序对（第一节）；
3. 再看是"整体发虚"还是"个别字发虚" —— 前者是图幅/密度问题（第三节），
   后者是字体分支问题（第二节）；
4. 最后才怀疑拆分代码。**渲染问题 90% 不在拆分逻辑里。**
