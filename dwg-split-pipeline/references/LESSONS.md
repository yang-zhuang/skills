# 经验配方（LESSONS）

改代码**之前**先翻这里 —— 这类问题以前踩过没有。

写法要求：**配方，不是散文**。每条写清「什么现象 → 怎么判 → 改哪里 → 改成什么」，
以及「试过但没用的做法」—— 后者能省掉下一次的重复尝试。

条目末尾的 `base:` 是这条经验成立时的 base 指纹（见 `../BASE.txt`）。
base 变过之后，靠 sha256 判断这条还适不适用。

### L-001 拆出来只有轴线 + 图名 + `‰`，墙体门窗全没有

- **现象**：拆出的图内容极少（实测 811 个实体只拿到 193 个），且所有图上都差不多。
- **判据**：程序自己就会拦下报 `T3RequiredError`（读图后数 `ACAD_PROXY_ENTITY` > 0）；
  或一行自检：`Counter(e.dxftype() for e in doc.modelspace())` 里出现 `ACAD_PROXY_ENTITY`。
- **改法**：**不是改代码，也不是「转一下 T3 就好」** —— 源图没导出成天正3（T3）。
  正确动作：**回天正**做一次图形导出（`TSaveAs` / 菜单『图形导出』→ 保存类型选『天正3』），
  导出后文件名通常带 `_t3`，用导出的那张来拆。本管线不代做这一步（2026-09-23 定，
  见 README「拆分对象」）。
- **试过没用**：①换 ODA 转 DXF（310 组码原样保留）、换 ezdxf 版本（不解析 310）；
  ②调外部工具自动转 —— 真天正图上脚本根本不执行（7 次实验全败），
  且 `TSaveAs` 对真天正图是**原样另存**（天正3 格式的定义就是保留 TCH 对象），
  转一遍补不回几何；要补几何必须在天正里 **EXPLODE 炸开**成基本图元再存，
  那是人工点几下的事。
- `base: 01177de`（2026-09-23 修订：删去「配 T3_CONVERT_CMD 自动转」的旧结论）

### L-002 渲出来字形放大、轴号撑破圆圈、数字变空心轮廓

- **现象**：轴号 ①②③ 与尺寸数字比原图粗一圈，圆形轴号被数字撑破；字形是空心的。
- **判据**：SHX 目录**注册晚于**第一次文字度量。ezdxf 的 `_CachedFont._glyph_caches`
  是**类级**字典，先解析成 TTF 替身就把结果缓存住了，之后注册 SHX 也不会重算
  （`font_manager.clear()` 清不掉它）。
- **改法**：`ensure_shx_support()` 必须在 `build_clusters()` **之前**调用
  （后者求 bbox 会触发文字度量）；并设 `shx_resolve_order = "stl"`（默认 `"tsl"` 是
  TrueType 优先，真 SHX 永远轮不到）。
- **试过没用**：只设 `support_dirs` 不改 resolve_order —— 替身 TTF 仍被优先选中。
- 详见 `RENDERING.md`。`base: 01177de`

### L-003 `titles` 非空但 `title_entities = 0` → `--title-mode` 静默失效

- **现象**：图名明明识别到了（json 的 `titles` 有值），但 `--title-mode=strip/auto`
  一点效果没有，图名大字还留在图上。
- **判据**：json 里 `titles` 非空而 `title_entities = 0` —— **这个组合不该出现**。
- **根因**：把「唯一一条关键词标签」兜底写进 `titles` 之后，
  `if titles: → _own_title_ents or _merged_ents` 恒为空。
- **改法**：`if titles:` 分支里补 `or [e for _, e in c["labels"]]` 兜底。
  口径必须与命名严格一致：**名字取自哪条文字，就剔哪条文字**。
- **自检**：`verify_split.py` 的 E4 会自动查这条。`base: 01177de`

### L-004 某个源拆出 0 张图，产物目录里只有 `split_report.json`

- **现象**：看着像"没跑"，其实是空图源。
- **判据**：源文件**恰好 12,991 字节** + `modelspace` 0 个实体（实测 3 个空壳：
  `星太总平图`、`后湖、_t3__F2照片`、`后湖、_t3__后湖第二批李彬`）。
  用 ODA 转 DXF 后 `ENTITIES` 段同样是 0。
- **改法**：**不是 bug**。天正批量导出跑了一次却只写出模板文件。
  空图源照样写完成标记 —— 以后源重新导出成有内容后，必须 `--force` 才会重跑。
- ⚠️ `--limit=5` 取的是体积最小的 5 个，实测正好把 3 个空壳全捞进来，别拿它冒烟测试。
- `base: 01177de`

### L-005 `margin=3000` 切不开 → 出现 4 万+实体的巨簇

- **现象**：几百张图该拆成几十张，结果其中一簇有 4 万多个实体，读起来是一坨。
- **判据**：`校验报告.json` 的 `huge_cluster`（单簇实体数 > 5000）。
- **改法**：调小 `--margin`。但**别只看簇数** —— margin 太小会把一张完整的图切碎
  （图内的门洞、房间分隔会断开），要靠视觉评估回来确认。
- **还没根治**：互相连通的图（比如两张平面共用一段墙线）本质上分不开，
  这时得靠人工指定或改判据。`base: 01177de`

### L-006 PNG 渲染失败：`invalid major axis: (0,0,0)`

- **现象**：某个序号目录里 dxf 正常、PNG 缺一张或两张全缺。
- **判据**：异常信息 `invalid major axis`。**退化椭圆/弧**（major axis 为 0）触发。
- **改法**：DWG 是好的，只有 PNG 失败。短期的补救是 `--rerender` 跳过或加防护；
  真要修得在渲染前过滤掉退化图元。
- `base: 01177de`

### L-007 图形被图名大字挤成一小块

- **现象**：渲出的图里细节糊成一团，一行很大的字占了半幅面。
- **判据**：json 里 `title_scale > 1.0`（实测「城市疏捞队门卫室」字高 7234，
  把包围盒横向撑到 **2.70 倍**）。
- **改法**：`--title-mode=auto`（识别到图名就剔除，命名仍用它）。
  **只摘图名，指北针/尺寸线/构件全部保留。**
- **试过没用**：调 margin（无效 —— 这是图幅问题，不是聚类问题）；
  调 `PNG_TARGET_LONG_PX`（只会让整体更大，挤压比例不变）。
- `base: 01177de`

### L-008 多模块同进程 import → `I/O operation on closed file`

- **现象**：`main.py` 跑起来后，跑一会儿就再也打不出任何字，报 I/O 错误。
- **根因**：模块里写 `sys.stdout = io.TextIOWrapper(sys.stdout.buffer, ...)`，
  多个模块被同一进程 import 时**重复包装**，旧 wrapper 被 GC 时关掉了底层 buffer。
- **改法**：只用 `sys.stdout.reconfigure(encoding="utf-8")`（幂等、不替换对象）。
  **禁止**再包一层 `TextIOWrapper`。
- `base: 01177de`

### L-009 改了源图重跑，转换器却说"跳过"或误报失败

- **现象**：转换器明明能跑，却一直沿用旧产物；或报"失败"但产物其实在。
- **根因**：转换器**自带断点续传**（`t3_export_progress.json`），已转成功的会跳过。
- **改法**：源图改过要重转，在**转换器侧**清进度记录（本仓不越权替它删）。
  ⚠️ **绝不要**在调它之前把旧产物挪走 —— 它会"跳过 + 产物不存在"→ 误报失败。
- `base: 01177de`

### L-010 拆出的平面图底部残留一条独立线段（**本次实测发现，根因待确认**）

- **现象**：`民族路108号` 拆出的 `02/二层平面布置图.dxf`、`03/三层…`、`04/四层…`
  底部各有一条粗线段，与主体图形明显分离（看图确认过）。
- **判据**：`校验报告.json` 的 `multi_component` → `gap_ratio` = **13.6% / 13.6% / 14.0%**
  （超过 5% 阈值）。三个簇都有，且比值几乎一致 → 说明是**同一类结构性原因**。
- **已排除**：`margin` 太小 —— 它和主体在**同一个簇内**，聚类阶段就没分开。
- **待确认的猜想**（未验证，别当结论）：疑似图名文字被剔除时，其下划线/引线是独立
  实体、没被一起摘掉。查 `split_dwg.build_clusters` 里 `title_ents` 的收集范围。
- **下一步**：视觉评估确认是不是图名残留；是的话改 `title_ents` 的收集逻辑，
  或把"图名附近的孤立短线段"一并纳入剔除集。
- `base: 01177de`
- **2026-09-28 复核（`团结大道1006附8号_t3`）**：视觉评估确认了这条猜想成立 ——
  01 的第二块是「项目概况 + 混凝土构件强度表」说明块（**属该图自带内容，保留**），
  02 的第二块是**图名下划线横条**（`LWPOLYLINE`，2 顶点，5×258px，纯装饰线）。
  两类都**只是正常分块**，`gap_ratio` 超阈值**不等于两张图没切开**。
  → **判据修正**：`multi_component` 只是"请视觉确认"的**提示**，不是 error；
  看图确认是"主体 + 说明块/装饰线"就判正常，不要去动聚类参数。

### L-011 图名取成构件标注里的括号注解（**2026-09-28 实测修复**）

- **现象**：`团结大道1006附8号_t3` 拆出的 `02` 文件名是「（余同）」，图上真图名是
  「二层结构平面图」——**文件名与图上大字完全对不上**。
- **判据**：`split_report.json` 里同一簇的 `labels` 已经是「二层结构平面图」，
  而 `titles`/`title_texts` 却是「（余同）」——**两个字段自相矛盾**就是本 bug 的指纹。
  另可看 `title_scale`：错的这张只有 0.04~0.07，正确的图名约 0.2~0.33。
- **根因（两层）**：
  1. 「（余同）」来自图上真实标注「KZ-1（余同）」的括号部分，它字高 289 **刚过**
     `TITLE_MIN_H=200` 阈值，被形态判据当成图名候选；
  2. **真图名与主体图形几何分离**（单独成小簇），命名时主体簇里"唯一候选"就是
     「（余同）」→ 按"唯一候选=高置信图名"规则**直接定名**，真图名后归并进来也翻不了盘。
- **改法**（改 `06_work/split_dwg.py`，两处，共 +57 -9）：
  1. 新增 `_TITLE_CONTINUATION = ("余同","同前","同上","详见","参见")` +
     `_is_title_stopword(t)`：单字停用词精确匹配、延续标记**含子串**匹配
     （这样全角/半角括号都能盖住，且不误伤「十三支沟门房（西）」这类真图名）。
  2. 命名时 **own 与 merged 候选合并后按 `_text_height` 取最大**，而不是 own 优先：
     `titles = [max(own+merged, key=字高)]`。图名永远比标注大，字高是最可靠的判据。
     ⚠️ 只在"两侧都有候选"时生效，单侧有候选时是恒等变换 → 不破坏绝大多数图的既有行为。
  3. `title_ents` 的收集口径必须和命名**同步改**，否则 strip 会失效。
- **验证**：`02` 改名成功、`01/03` 不受影响、实体数 222/184/31 不变、校验 PASS。
- `base: 01177de`（sha256 见新作业的 `BASE.txt`）

### L-012 视觉评估这一步不能省（**2026-09-28 流程教训**）

- **现象**：只跑 `main.py` + `verify_split.py` 就交付，`verify_split` 返回 PASS ——
  但图名错误、图例混入这类问题**一个都没发现**。
- **根因**：`verify_split.py` 自己的 docstring 就写了它只管**能算准的**（实体数守恒、
  产物齐全、图面非全白），**语义判断明确交给视觉 agent**。跳过第 4 步 = 只验了一半。
- **判据**：`校验报告` verdict=pass **不等于**拆分合格。凡是"图名对不对得上""这是不是
  一张完整独立的图""这块内容该不该在这张图里"，**只能看图**。
- **纪律**：`split_report.json` 的字段自相矛盾（如 `labels` vs `titles`）是**脚本能自动
  发现但当前没检查**的信号，可用于以后给 `verify_split.py` 加一条 E6 判据。
- `base: 01177de`

### L-013 按图层名剥离附属块 → 误伤别图（**2026-09-28 实测，附功能实现**）

- **需求**：图名以下的「设计说明 + 材料表」要从主图剥掉，且**各自单独出 dxf**（不许合并）。
- **⚠️ 陷阱**：**不能只按图层名判断**。实测 `团结大道1006附8号_t3` 里，`PUB_TEXT` 图层
  同时被两处使用：① 01 图下方的设计说明（x≈-14814~-7010）；② **03 图（倾斜观测示意图）的测点
  标注**（CIRCLE + TEXT `1/2/3`，x≈34000~37000）。按图层一刀切会把 03 图的测点剥走 → 03 图废掉。
- **改法**：识别要用「**图层 + 位置**」双条件 ——
  实体既要在 `ATTACH_LAYER_KINDS` 图层里，**又要落在该簇自己的 bbox 内且底边 y < 该簇图名线 y**。
  - 位置判据取**底边**而非上边/中心：材料表顶线 y=9844 只比图名线低 829，用上边/中心会漏掉紧贴图名那行。
  - 实现落在 `split_dwg._split_attachments()`，在 `build_clusters()` 出口调用，产出
    `c["main_ents"]` / `c["attachments"]`；主图导出改用 `main_ents`，附属块复用 Binary DXF
    写法但**不出 PNG/json**。
- **守恒口径要同步改**：主图少了 N 个实体，`verify_split` E1 必须改成
  「报告合计 **+ 附属块** == 源图」，否则会误报不守恒。另加 `attachment_missing` 检查
  （报告里写了附件但文件不存在 = error）。
- **验证**：01 主图 222→180（-42=23+19），主图 `PUB_*` 残留 0；02/03 不变（03 测点仍在）；
  视觉三重印证（视觉 + 像素扫描 + DXF 结构）通过。
- **换图提醒**：`ATTACH_LAYER_KINDS` 的映射（PUB_TEXT=说明 / PUB_TAB=表）是**本图实测**结论，
  换图先看 `split_report.json` 的 `attachments[].texts` 复核。
- `base: 01177de`
