# 检查项依据

每项检查都写明「为什么判它」和「阈值从哪来」。阈值改动必须同时改这里，
否则报告里的数字没人看得懂。

## 静态检查（不启浏览器，纯文本）

| 检查 | 硬/软 | 依据 |
| --- | --- | --- |
| 图片域名合法 | 硬 | 微信正文只认 `mmbiz.qpic.cn`。本地路径、第三方 CDN 在客户端显示裂图。提交前必须跑 `media/uploadimg` 换成 mmbiz 链接 |
| 样式已内联 | 硬 | 保存时 `<style>` 与 class 选择器被剥离，外挂在身份丢失就等于没写样式 |
| 无微信禁用标签 | 硬 | `script` / `iframe` / `style` / `form` / `embed` 会被整节点剔除，残骸会污染正文 |
| 无会被剥离的属性 | 硬 | `class` / `id` / `on*` 事件属性必被移除；依赖它们的样式与交互全部失效 |
| 无固定宽度溢出 | 硬 | `width` 大于视口宽时，移动端必然横向滚动。微信宽度自动不超过屏宽，因此应写 `max-width: 100%` |

## 浏览器检查（真实渲染）

| 检查 | 硬/软 | 依据 |
| --- | --- | --- |
| 无横向溢出 | 硬 | `documentElement.scrollWidth > 视口` 即证明读者会左右拖。宽表格是头号元凶 |
| 图片可加载 | 硬 | `naturalWidth == 0` 说明资源没回来，等同于读者看到破图 |
| 正文字号可读 | 软 | 阈值 12px。低于此值 iOS 上接近不可读，但存在刻意的注释小字场景，故不判死 |
| 元素未超出右边界 | 软 | 单个元素 `rect.right` 越界。多数由 `padding` 与固定 `width` 叠加造成，属可控瑕疵 |
| 标题层级数不超限 | 软 | 检出超过 3 级粗体标题。移动端 375px 下超过 3 级已无法用字号字重做视觉区分，但不一定算错 |

## 为何标题上限是 3 级

- 对编辑器**渲染后 DOM** 的逆向分析（2026）只列出 `h1–h3`，h4–h6 未进可用集
- 另有资料笼统称 h1–h6 均不被过滤，但双方都承认 h4 以下行为不稳定
- 文章主标题由后台字段承载并渲染为页面级 h1，正文再用 h1 语义冲突

综合结论：正文最多 3 级，且用 `<p>` + 内联 `font-size`/`font-weight` 表达而非 `<h*>` 标签——
字号字重是唯一洗不掉的层级表达方式。渲染器对超出部分会降级并在 `heading_warnings` 里告警，
**降级必须可见，不能静默发生**。

## raw 对比的意义

`--raw` 传入未经 `wechat_guard` 清洗的产物，脚本会分别渲染两版。
对比 `page.raw.html` 与 `page.html` 的截图，能直接看出**微信洗掉了什么**。

只看清洗后的成品就等于默认微信没洗手——而实际上第三轮清洗（客户端渲染）的行为
从来不和文档同步更新。
