# 分层分析法（通用）

## 总原则

分层的目的不是把流程拉长，而是让**每层可独立消费、可随时停、结论不串味**。
层与层之间只传两样东西：本层证据（带等级）和交给下一层的待验证问题。

「MINIMAX-H3提速500高画质」在下文只用来演示**怎么拆**，不构成镜像检查清单。
后续镜像的名字举不完，维度始终按当前问题组织，不套固定表。

---

## L0 名称声明拆解

**入口**：只有应用名 / 镜像标题，还没连实例。

**判定问题**：这个名字承诺了什么？哪些是可证伪命题，哪些只是形容词？

**判定动作**：

1. 切出三段：主体（模型 / 框架名与版本）、修饰词（提速 / 高画质 / 长上下文等）、数字 + 单位（500 究竟是 tok/s、倍数还是别的？）。
2. 每条承诺改写成可证伪句。例如把「提速500」写成「在某上下文中 decode 达 500 tok/s，且给出并发与量化档」；条件没给出就记「口径未定义」。
3. 标证据等级：只有名字作为来源 → **官方**；连名字都没说清 → **未核实**。此层绝不出现「实测」。

**退出**：声明清单，每条带「待验证条件」与等级。

**常见误判**：把「500」默认成 tok/s；把「高画质」当成已测质量；把作者自述当本机事实。

---

## L1 镜像静态信息

**入口**：拿到镜像页 / 镜像 ID，或已能读镜像内文件。

**判定问题**：镜像装了什么、怎么启动、声明的依赖是否齐全？

**判定动作**：读社区页描述与镜像内 `README`、启动脚本、`requirements`、config；记下版本、预置权重路径、默认端口、启动命令、是否带 API key。
发现缺件只记录，不在此层下性能结论。

**退出**：环境清单 + 启动方式；证据等级为 **官方 / 源码**。

**常见误判**：把镜像页的安装说明等同于实例上真实跑起来的参数（那是 L3 的事）。

---

## L2 实例体检

**入口**：SSH 已连通。

**判定问题**：这台机器实际能给多少资源？与 L0 声明的隐含前提是否一致？

**判定动作**：复用 `../autodl-remote-shell/scripts/autodl-instance-probe.sh`；重点看**真实 cpu.max**（不是 `nproc` 的宿主虚值）、显存总量、数据盘可用量、内存上限、PATH 与 turbo 状态。
动手下载前先写容量账：这台机器能吃下哪个尺寸、能同时放几个。

**退出**：容量账 + 体检原始输出（留项目台账）。

**常见误判**：用宿主核数当容器配额；假定 `/root/autodl-tmp` 一定是独立数据盘——必须用 `df` 实证（本 skill 的 `ssh-connection.md` 附录就记录了一次挂 overlay 30G 的实测）。

---

## L3 运行时与配置

**入口**：服务已启动或可启动。

**判定问题**：实际跑起来的参数是什么？与 L1 文档和 L0 宣称一致吗？

**判定动作**：用 `tr '\0' ' ' < /proc/<PID>/cmdline` 看真实命令行；读 config 的 args；`curl /health`；查监听端口；确认模型版本、量化档、视觉模块、上下文长度。
改过 config 后必须确认服务已重启，否则看的还是旧进程。

**退出**：运行时事实表（**实测 / 源码**），与宣称不一致处单列一栏。

**常见误判**：改了配置没重启；只读文档不看 cmdline；把「配置里写了」当成「效果已验证」。

---

## L4 受控实测

**入口**：有明确的声明要验，且 L2/L3 已完成。

**判定问题**：锁住哪些变量后，这条声明成立 / 不成立？

**判定动作**：

- **速度类**：预热 3~5 次取后几次；每次换数据；A→B→A→B 交叉对照；指标写清是 decode 速度还是首包延迟。
- **画质 / 效果类**：固定输入输出对照，锁住随机种子与其它参数；主观判断与客观指标分列。
- **每条实测都记条件**：模型版本、量化档、上下文、并发、worker 数、实例配置。
- **ComfyUI API 提交格式**：`POST /prompt` 的请求体必须是 `{"prompt": <工作流对象>}`，并剥掉 `_api_config` 等非节点字段；直接把工作流 JSON 当 body 会得到 `no_prompt`。这是**请求格式错**，不是镜像故障——先看返回体再归因，别急着下"节点坏了"的结论。
- **画质对照怎么取帧**：到 `output/` 按 prompt_id 或提交时间定位本轮产物（别拿历史文件）；用 ffmpeg / PIL 在**相同时间点**（如 0 s 与 1.5 s）截帧，同 seed 并排看。两版构图不同 = 不同生成轨迹，不能归因到画质开关。
- **镜像自带的「基础版 / 加速版」不等于单变量 A/B**：先比对两版节点集合与关键输入（步数、采样器、注意力后端、帧数公式），把能锁的都锁上；**帧数常写在不同 widget 里**（本次基础版是 `141.value=2`、加速版 `141.value=5`），对照前要逐项拉平并记录改了哪几个字段，只留"加速方案"这一个变量；节点结构本身不同时，测到的是「整包方案差异」，不能归因到某一个加速开关，画质差异也不能归因为画质档。
- **一次 A/B 只能算上界，不能算倍数**：首个版本含冷加载、后一个吃缓存，顺序本身带来系统偏差。要给出可写进结论的倍数，必须①预热 3~5 次取后几次中位数；②A→B→A→B 交叉跑（抵消顺序偏差）；③各次换不同提示词/数据（防单条 prompt 巧合）；④按"端到端墙钟 / 每步耗时 / 首帧延迟"分开记，三者不混比。缺任一条，结论写"单次观察、上界"，不写"实测加速 N 倍"。
- **显存峰值必须采样，不能用文件体积或空闲显存代替**：生成任务启动前开后台采样
  `nvidia-smi --query-gpu=memory.used,memory.total,utilization.gpu --format=csv,noheader -l 1 > peak.log`，
  任务结束后取 `memory.used` 最大值；同时记分辨率、帧数、步数、TE 是否在 GPU、启动参数，否则峰值不可复用。
  `/system_stats` 的 free 只是任务前空闲值，不是峰值。
- **要下"画质更好/更差"的结论，必须做同结构只切开关的对照**：拿同一份工作流，只启用/停用加速节点
  （Block Cache / Turbo LoRA / 注意力后端），其余节点、seed、prompt 完全一致。整包两版构图不同属于
  不同生成轨迹，只能说"有可见差异"，不能归因到画质档。

**退出**：成对结论——成立条件 + 不成立条件，每条附证据等级与原始输出位置。

**常见误判**：冷启动当稳态；同一条 prompt 复读；用「GPU 100%」判断瓶颈；不同口径的数字直接比大小；把整包工作流对照当成单一开关的因果结论。

---

## L5 结论分层与归档

**入口**：任一层已有结果。

**判定问题**：谁在什么时候消费这份结论？

**判定动作**：

1. 每条结论标四级证据：**实测 / 源码 / 官方 / 未核实**，查不到就留空。
2. 固有规格（模型版本、量化档、控制能力、许可证、钉死版本）进规格卡；实例数值（磁盘余量、单次 tok/s、PID、pip 源）留项目台账。详见 `evidence-and-ledger.md`。
3. 结果页只放规格入口；规格页给选型阶段看；方法对照实验单独成页（需要时才做）。

**退出**：报告 + 台账。报告里「镜像宣称」与「本机实测」分栏，不混写。

**常见误判**：把一次实例数值写成通用结论；把「官方说支持」写成「本机通过」；把规格表塞进结果页让看结果的人扫无关字段。
